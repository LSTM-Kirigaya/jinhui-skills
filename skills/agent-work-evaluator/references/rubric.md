# Agent 作品双轨评分量表

## 1. 类型判定

### 开箱即用 Agent 软件

用户安装、配置或登录后即可完成真实任务。重点考察任务完成率、交互、稳定性、恢复、安全和结果交付。UI 不必华丽，但核心路径必须完整。

### Agent 框架 / Harness

开发者用其构建不同 Agent。重点考察 Agent Runtime、状态模型、工具协议、上下文管理、子 Agent、扩展性、持久化、测试和兼容性。只有固定 Demo 而没有稳定抽象，不能视为成熟框架。

### 混合型

分别按软件轨和框架轨取证，再检查：

- 上层软件是否真实调用所提交框架；
- 软件成功是否能追溯到底层运行记录；
- 第三方是否能绕过上层 UI 独立复用框架。

两者未连通时，不得用上层 Demo 替底层框架背书。

## 2. 五项评分

### 2.1 场景价值与行业可复制性（25%）

共同问题：目标用户是否明确、问题是否真实、Agent 是否比脚本或聊天更有价值、效果是否量化、能否迁移到其他环境。

软件轨重点：

- 核心任务能否开箱完成；
- 配置成本、用户路径和交付结果；
- 真实用户、案例、成功率、耗时或成本证据。

框架轨重点：

- 是否解决开发者的通用工程问题；
- 新模型、工具、存储和执行环境接入成本；
- 是否支持多个真实用例，而非只适配一个 Demo。

| 分数 | 锚点 |
|---:|---|
| 0–2 | 场景模糊或只有概念包装 |
| 3–4 | 场景成立但效果未验证、复制依赖强 |
| 5–6 | 有可运行案例和明确价值，迁移仍有成本 |
| 7–8 | 有真实使用与量化效果，可低成本复制 |
| 9–10 | 规模化验证并形成成熟复制方法 |

### 2.2 Agent 协同与自主闭环能力（25%）

共同问题：是否有模型—工具—反馈循环、动态计划、真实成功判定、失败传播、重试/回滚、暂停恢复和人工介入。

软件轨重点：

- 用户任务能否端到端完成；
- 中断和失败后的恢复体验；
- 进度、工具调用和敏感操作是否透明；
- 是否减少用户持续监督。

框架轨重点：

- Runtime、状态机和执行语义；
- 子 Agent 独立上下文、委派、并行、取消和结果汇聚；
- Checkpoint、Resume、Interrupt、异步任务和错误传播；
- 上述能力是否有测试。

不能单独认定为多 Agent：多阶段命名、多个 Prompt 共用上下文、串行调用多个 API、固定 DAG、把模块名称叫 Agent。

| 分数 | 锚点 |
|---:|---|
| 0–2 | 没有真实 Agent Loop，主要是脚本、标签或占位 |
| 3–4 | 有工具调用或固定工作流，闭环和恢复较弱 |
| 5–6 | 基本闭环成立，具备状态、重试和任务拆解 |
| 7–8 | 长任务、多 Agent 隔离、委派、恢复和人工介入可靠 |
| 9–10 | 复杂真实任务中稳定自主规划、并行协作和自适应 |

### 2.3 Skill 工程体系与生态复用（25%）

共同问题：是否有 Skill 规范、注册与发现、按需加载、输入输出约束、依赖、权限、版本、组合、测试和第三方复用。

软件轨重点：

- 用户能否安装、启停、配置和升级 Skill；
- Skill 权限和来源是否透明；
- 第三方扩展是否会破坏主程序。

框架轨重点：

- 稳定的 Skill API 或文件标准；
- 渐进加载和运行时选择；
- 工具、脚本、模板、参考资料的组合；
- 生命周期、兼容性、测试和分发机制。

README 写“支持 Skill”、一个 `skill` 字段、固定工具列表或若干无加载器的 Markdown 文件都不足以构成 Skill 体系。

| 分数 | 锚点 |
|---:|---|
| 0–1 | 只有概念或字段，没有实现 |
| 2–3 | 有可复用 Prompt/工具，但无规范和生命周期 |
| 4–5 | 有基础格式、加载器和实例 |
| 6–7 | 支持发现、按需加载、依赖、权限、测试和组合 |
| 8–9 | 标准稳定、工具链完善、有第三方生态 |
| 10 | 形成广泛采用且可治理的生态标准 |

### 2.4 工程落地、运行验证与安全可审计（20%）

共同问题：能否干净安装、依赖是否锁定、测试与 CI、错误处理、超时、并发、日志、Tracing、权限、凭证、沙箱、人工审批和审计真实性。

软件轨重点：

- 安装、升级、配置和数据迁移；
- 崩溃恢复、长时间运行和核心任务成功率；
- 隐私、权限与敏感操作确认。

框架轨重点：

- API/类型稳定性、模块边界和兼容性；
- 并发与状态一致性；
- Backend、Sandbox、Permission、Telemetry 等接口；
- 单元、集成、端到端、性能和安全测试。

| 分数 | 锚点 |
|---:|---|
| 0–2 | 无法复现，缺测试，存在伪验证或严重安全问题 |
| 3–4 | Demo 可运行，但环境依赖和质量保障较弱 |
| 5–6 | 基本部署、测试、日志和错误处理齐备 |
| 7–8 | CI、权限、恢复、监控和安全机制完整 |
| 9–10 | 规模化生产验证，有系统评测、安全治理和稳定性数据 |

### 2.5 开放与开源贡献（5%）

共同问题：许可证、核心源码、可构建性、文档、示例、版本、Changelog、Issue/PR、外部贡献和 Demo 可追溯性。

不要直接按 Star 打分。Star、Fork 和贡献者数量只能作为社区活跃度旁证，不能替代代码质量。

| 分数 | 锚点 |
|---:|---|
| 0 | 未开源或许可证不明确 |
| 1–2 | 代码可见但核心缺失、不可构建或不可复用 |
| 3–4 | 有许可证和主要源码，发布与社区较弱 |
| 5–6 | 可构建、可复用，有基本版本和贡献流程 |
| 7–8 | 社区活跃、维护规范、稳定发布和外部贡献 |
| 9–10 | 形成有影响力的开放标准或基础设施 |

## 3. 证据不足时的分数上限

这些是默认上限；若有更强反证可以更低，若要突破必须写明新证据：

- 只有 README 声明、没有实现路径：对应能力不高于 2 分；
- 主要实现是占位、模拟或固定返回：对应能力不高于 3 分；
- 只有无法追溯版本的线上 Demo：工程相关能力不高于 5 分；
- 没有自动化测试：工程项通常不高于 4 分；
- 安全、测试或审计硬编码通过：工程项通常不高于 2 分；
- 宣称多 Agent，但无隔离、委派与汇聚：Agent 协同项不高于 2 分；
- 宣称 Skill，但无规范、加载器和实际 Skill：Skill 项不高于 1 分；
- 核心能力在未提交外部服务：该能力仅按可验证的调用集成评分，不按完整实现评分；
- 无法在干净环境复现且无可信发布产物：总分通常不高于 5 分；
- 许可证缺失或限制不清：开源项不高于 2 分。

## 4. 计算与用户校准

默认加权总分：

```text
总分 = 场景价值×0.25 + Agent协同×0.25 + Skill工程×0.25
     + 工程落地×0.20 + 开源贡献×0.05
```

先给出“证据基线分”，再接受用户对参照物、权重和品味偏好的校准。报告必须并列保留原始分与校准分。用户偏好可以改变价值判断，不得改变源码是否存在、测试是否通过等事实。
